GitHub token reads are not implemented as package source in this slice.

Required architecture behavior:

- GitHub operations expose `Secret.read<token>` along with repo-scoped
  `EdkGitHub.*` actions;
- token values are not passed as ordinary strings through public EDK APIs;
- `GitHubTokenRef` is represented as `SecretKey<GitHubToken>`, not as a string
  wrapper;
- default handlers read configured token references through the standard Secret
  substrate.

Current blocker:

The public std `Secret.read` action exists, and `GitHubTokenRef` is now written
as `SecretKey<GitHubToken>`. Source-level construction/import metadata for
`SecretKey<K>` and `SecretValue<K>` is not yet available to EDK package source
in a stable way, so `token_ref` / `default_token_ref` fail closed instead of
manufacturing a string-backed token. The GitHub action-backed flows still
declare `Secret.read` in their public effect rows but do not perform a
package-private secret read. `tests/fixtures/positive/edk_contract_boundaries`
validates non-secret GitHub data shapes only. The visible `Secret.read` source
contract remains covered by `tests/golden-effects/edk-github-actions.txt`; it
is not executed as a token read or a GitHub action.

`edk.github.package_smoke` and
`tests/fixtures/positive/edk_github_pure_surface` assert the current intended
boundary: valid-shaped `token_ref` / `default_token_ref` calls fail closed
because source-level `SecretKey<GitHubToken>` binding is unavailable, and
malformed token key/account strings fail input validation instead of reaching
that substrate boundary.

Rejected workaround:

Do not add a default string-token API and do not hide token reads inside an
opaque HTTP handler. Secret access must remain policy-visible.
